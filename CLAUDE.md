# EXR Quick Look

Open source macOS Quick Look extension giving Finder correct thumbnails and previews for modern OpenEXR files.

Full specification: @docs/exr-quicklook-plan.md — read it before starting work in a new session.

**Phase 2 built 2026-09-06.** `Tools/bake-lut/bake.py` bakes a 65³ LUT from OCIO 2.5.x built-in
`studio-config-v4.0.0_aces-v2.0_ocio-v2.5` (6 SDR views), default view
`ACES 2.0 - SDR 100 nits (P3 D65)`, plus OCIO golden images in CI. Thumbnail and
preview both always render P3 — thumbnails are cached display-independently, so

with `ociobakelut --format icc` from the same pinned OCIO config instead
(OCIO is BSD-3-Clause). See @docs/aces-transform-options.md §7.

A third-party app extension can claim `com.ilm.openexr-image` and overrides
Apple's rendering for both thumbnails and previews on macOS 26.6.2. Written up
in @docs/uti-findings.md.

Reboot survival verified 2026-09-05: 4/4 via `Tools/post-restart-check.sh`.
Outstanding from Phase 0: Spotlight and Open dialogs, and behaviour on
macOS 14/15, are untested (see uti-findings §6).

LUTs are baked from the ACES 2.0 **Studio** config (6 SDR views); HDR views and
HDR-encoded displays are excluded until there is EDR output. The assumed-input
list (18 scene-linear spaces, Nuke/Resolve-like) is generated by
`Tools/bake-lut/gen_spaces.py`, with chromaticities derived through OCIO rather
than transcribed, validated to 1.4e-06 against OCIO's own matrices.

**Known limitation:** the extensions
cannot read the shared App Group under ad-hoc signing — macOS denies them by
System Policy without a Team ID, and there is no alternative storage route
(direct file access fails identically). So the host app shows no preferences at
all; the plumbing stays in `EXRPreferences` for a fork that signs its own build,
and the App Group is not even opened unsigned (it triggers a TCC prompt for
nothing). This project will not be signed. See phase1-status.md.

## Non-negotiable decisions

These were settled deliberately. Raise it with me before deviating from any of them.

1. App extension architecture — host app plus thumbnail and preview extensions. `.qlgenerator` is dead as of macOS 15.
2. Link the OpenEXR reference library, not TinyEXR. TinyEXR has no DWAA/DWAB support and won't add it. DWAA is a hard requirement.
3. ACES 2.0 output transform, baked to a 3D LUT at build time.
4. Zero runtime dependencies. No OCIO, no `$OCIO`, no assumption that Nuke or any other application is installed.
5. Render to Display P3, tag the output, let ColorSync handle the display.
6. Crop to the display window by default.
7. Thumbnail and preview render identically by default. A user-set preview override may diverge, and must be visibly badged when it does.
8. No auto-exposure, no per-image normalisation, ever. It would give every frame of a sequence a different brightness.
9. Committed preferences, set in the host app window: (a) assumed input
   colourspace when the file has no chromaticities, default ACEScg; (b) default
   view transform. **Amended 2026-09-06** — the plan's original D9 allowed only
   (a). The Quick Look preview overlay may transiently override either, badged,
   per D7. Anything beyond these two still needs sign-off.

   **Amended again 2026-09-06 — input override no longer stands down.** The plan
   (§8, and the §10 checklist) said the input-space override applies only to
   files with no `chromaticities`, and stands down on files that declare their
   own, because "silently overriding a file that told the truth" causes wrong
   colour. That rule assumed the file's metadata is trustworthy. EXRs are
   normally image sequences, and when a profile has been misapplied it is
   misapplied to every frame — so standing down means the correction evaporates
   on the next arrow press, defeating the case the rule protects. The override
   now carries unconditionally, like the other view-side settings. The
   protection the rationale actually cares about is kept: it is badged whenever
   active, has one-click reset, and lapses on the §8 idle timeout. Plan §8's
   control table ("only meaningful when the file is ambiguous") and the §10
   checklist item are superseded by this.

   **Amended 2026-10-06 — `colorInteropID` counts as the file stating its
   space.** OpenEXR 3.4 added this standard attribute (a Color Interop Forum ID
   such as `lin_ap0_scene`). Precedence is now: explicit override →
   `chromaticities` → a recognised scene-linear `colorInteropID` → assumed
   default. IDs map through the table `gen_spaces.py` generates, taking each
   ID from OCIO itself (`getInteropID`), never typed in. Log and
   display-encoded IDs are ignored (primaries alone would render them wrongly)
   and the info panel says so. An ID of `data` makes every layer a data pass.

   **Amended 2026-10-07 — `arnold/color_space` is read too**, after
   `colorInteropID`: override → `chromaticities` → `colorInteropID` →
   `arnold/color_space` → assumed default. The value is an OCIO colour-space
   name, matched against each space's OCIO name *and aliases* (generated by
   `gen_spaces.py`, so ACES 1.x spellings such as "Utility - Linear - sRGB"
   match). Arnold's built-in-manager name `linear` maps to linear Rec.709 —
   its default rendering space since Arnold 5 — for that attribute only.
   Anything else (display spaces, unknown names) is ignored and the info panel
   says so. Real files in the corpus carry `ACEScg` and `linear`.

   **Amended 2026-10-07 — PQ HDR masters as input entries.** The input picker
   (and the assumed-default preference) may also name an *input transform*,
   not only primaries: `pq_p3d65_1000`, `pq_p3d65_4000`, `pq_rec2100_1000`.
   A PQ EXR is display-referred, so each is OCIO's **inverse** of the ACES 2.0
   HDR output transform (ST2084-P3-D65 / Rec.2100-PQ display), baked to a 65³
   LUT with PQ code values as its bounded domain, output scene-linear ACEScg;
   then the normal SDR view. Matches OCIO's full chain to 0.07/255 mean.
   Never applied automatically: real PQ files carry no tag (Netflix Cosmos
   Laundromat, Nocturne). Raw still shows the file's own code values.
10. Permissive licence — **BSD-3-Clause, chosen 2026-10-06** (`LICENSE`).
    Never copy from GPL sources. Bundled-library notices live in
    `THIRD_PARTY_NOTICES.md` and are copied into the app bundle.

## Non-goals

No editing. Never writes EXR. No deep data rendering. No sequence playback. No colour management UI beyond the one fallback preference and the transient preview overlay.

## Hardening rules

The equivalent Apple decoder shipped a zero-click heap overflow (CVE-2026-28977) from unchecked allocation arithmetic on unbounded image dimensions. We are writing the same class of code.

- Checked arithmetic (`__builtin_mul_overflow` / `__builtin_add_overflow`) on every operation feeding a buffer size. Every one, not most.
- Hard upper bounds on width, height, pixel count, channel count, part count, tile counts. Reject rather than clamp.
- Decode deadline and memory ceiling. On breach, fail to the generic icon. Never crash, never hang.
- Treat every input as hostile.
- **The memory ceiling must cover OpenEXR's own allocations**, not just ours:
  a decompressed chunk holds every channel of the part, and a tiled part read
  as scanlines caches a full-width row of tiles (`kMaxChunkBytes`, `kMaxTiles`).
- **The file can change between opens.** Anything sized from one open must be
  re-checked against the next (`decode_layer` re-reads the data window).
- **File text is untrusted in the UI too**: control and direction characters
  are stripped before display (`printable()` in exr_api.cpp).
- **Keep OpenEXR current.** Check its security advisories before every release
  (`gh api repos/AcademySoftwareFoundation/openexr/security-advisories`); the
  pin went stale once (3.4.5 shipped in 0.1.0, 29 applicable advisories behind).
  Adversarial review and its proofs: phase1-status.md "Adversarial review".

## Working agreement

- **Phase 0 is answered** and written up in `docs/uti-findings.md`. Raise it before building anything that depends on a different UTI outcome.
- **Build through `EXRCLI` first.** Quick Look extensions are painful to debug and `qlmanage` cannot see them. All logic lives in `EXRCore` and is validated through the command-line harness before the extensions are touched.
- **Verify, don't assume**, on anything version-dependent — particularly which tool currently generates the ACES 2.0 transform. Never silently substitute an approximation.
- Work one phase at a time. Ask before starting the next.

## Commands

Build order matters: openexr -> bake-lut -> build-core -> build-app.

```bash
Tools/make-spike-fixtures.py   # generate the Phase 0 .exr fixtures
Tools/build-openexr.sh         # once: pinned OpenEXR/Imath universal static
Tools/bake-lut/bake.py         # once: bake ACES 2.0 LUTs (needs PyOpenColorIO)
Tools/build-core.sh            # universal libEXRCore.a
Tools/build-app.sh           # build universal + ad-hoc sign -> build/EXR Quick Look.app
Tools/install.sh         # install to ~/Applications, register with LS + PluginKit
Tools/package-release.sh       # tests, then the styled dist/EXR-Quick-Look-<version>.dmg
Tools/status.sh          # registration, enablement, UTI assignment
Tools/finder-test.sh     # fresh uncached folder, opens in Finder
Tools/watch-log.sh       # live invocation log
Tools/post-restart-check.sh    # after a reboot: does registration survive?
Tools/uninstall.sh       # remove and deregister
Tools/fetch-openexr-images.sh  # official ASWF test corpus into Vendor/ (gitignored)
Tools/test-reference-corpus.sh # run that corpus through EXRCLI

build/uiguard <app> [--at x,y] # OK only if <app>'s window is topmost at that point
build/realclick x y [hold-ms]  # REAL mouse click via CGEvent -- always uiguard --at first
build/realmove x0 y0 x1 y1     # real pointer movement, for hover-latency tests
Tools/make-icns.sh             # logo -> conforming macOS 26 icon tile -> EXRPreview/AppIcon.icns
Tools/make-icon                # logo -> transparent art (edge flood fill); not used for the app icon
Tools/make-notices.sh          # THIRD_PARTY_NOTICES.md from the pinned sources' licences
Tools/corpus/build_corpus.py   # real-world EXR headers into Vendor/corpus/ (Range requests, ~200 MB)
Tools/corpus/manifest.py       # -> Tests/Fixtures/realworld/ (names only), used by test_realworld

build/bench <files>            # thumbnail / preview / exposure timings vs the §6.7 budget
Tools/fuzz.sh [secs] [workers]  # ASan+UBSan mutation fuzzer over the public API; crashers -> build/fuzz/crashes
build/qlprobe <files>          # headless: classify QL thumbnails by colour
build/qlpreviewprobe <files>   # headless: drive a real QLPreviewView
build/qlpanelprobe <files>     # the real spacebar panel, stepping items like ↓
build/utitool <files>          # show the UTI LaunchServices assigns
```

**Do not install Xcode.** Full Xcode is not on the dev machine and is not
needed: CLT provides `notarytool`, `stapler`, `iconutil`, `swift test` and a
working CMake + C++ → Swift universal static-link path (verified, not assumed).
Only `actool` and `ibtool` are missing, so **no asset catalogs and no
storyboards** — ship a plain `.icns` via `CFBundleIconFile` and build views in
code. Rationale and the full audit: `docs/uti-findings.md` §5.6.

There is consequently **no `.xcodeproj`**. Plan §5 assumes one; Phase 1 needs a
decision on whether to add it or keep the script-based build.

Release signing is blocked on something unrelated: no Developer ID certificate
exists in the keychain (`security find-identity -v -p codesigning` → 0 valid
identities). Phase 5 needs an Apple Developer Program membership.

Always reset the Quick Look cache before judging a thumbnail change, and trust
the log over what Finder shows — see `docs/uti-findings.md` §4.

**Never measure UI latency with `osascript … click at`.** It presses the
accessibility element and sends no mouse event, so it measures a path no user
takes. Use `build/realclick`, guarded by `build/uiguard --at`.
